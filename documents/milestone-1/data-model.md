## Document Table

The `document` table stores metadata for each uploaded document. The actual file contents are stored separately in object storage.

| Column            | Type           | Null | Constraints / Behavior                                                                                     |
| ----------------- | -------------- | ---- | ---------------------------------------------------------------------------------------------------------- |
| `document_id`     | `UUID`         | No   | Primary key. Generated by the application as UUIDv7 before persistence.                                    |
| `owner_subject`   | `VARCHAR`      | No   | Stable subject identifier from the authenticated identity system. Never accepted from client request data. |
| `file_name`       | `VARCHAR(255)` | No   | Validated user-facing filename. Case-sensitive. Unique within an owner's document space.                   |
| `file_size_bytes` | `BIGINT`       | No   | Actual accepted file-part size in bytes, derived by the server. Must be greater than zero and no greater than 104,857,600 bytes (100 MiB). |
| `content_type`    | `VARCHAR(100)` | No   | Canonical MIME type determined from file contents. Must be one of the supported content types.             |
| `uploaded_at`     | `TIMESTAMPTZ`  | No   | Generated by PostgreSQL when the metadata row is created. Defaults to `CURRENT_TIMESTAMP`.                 |

### Table Constraints

**Primary key**

```text
PRIMARY KEY (document_id)
```

**Unique filename per owner**

```text
UNIQUE (owner_subject, file_name)
```

This permits:

```text
Alice -> report.pdf
Bob   -> report.pdf
```

but prevents:

```text
Alice -> report.pdf
Alice -> report.pdf
```

Duplicate-name handling occurs in the application by rejecting an upload when the same owner already has the filename. The database constraint remains the final integrity guard.

Filename validation occurs before persistence. Milestone 1 rejects filenames that are missing, empty, whitespace-only, longer than 255 characters, contain `/` or `\`, contain NUL or other control characters, or are exactly `.` or `..`. Invalid filenames are not truncated or silently rewritten.

**File-size constraint**

```text
file_size_bytes > 0
AND
file_size_bytes <= 104857600
```

`file_size_bytes` records the actual accepted document size, not the overall multipart request size or a client-provided size value.

**Allowed content types**

Milestone 1 supports:

```text
application/pdf
text/plain
image/jpeg
image/png
```

The database should reject other persisted MIME types. File type is determined through content inspection rather than trusting the filename extension or client-provided `Content-Type`.

### Object Storage

No separate `storage_key` is stored during Milestone 1.

The object-storage key is deterministically derived from `document_id`, for example:

```text
documents/{document_id}
```

Because document contents are immutable, one document ID maps to exactly one stored object for the lifetime of that document.

### Indexes

The following indexes are required:

```text
PRIMARY KEY (document_id)
```

Created implicitly by the primary-key constraint.

```text
UNIQUE (owner_subject, file_name)
```

Created to enforce filename uniqueness within an owner's document space and support filename lookups.

```text
INDEX (owner_subject, uploaded_at)
```

Supports the primary listing access pattern:

SELECT documents belonging to the authenticated user ordered by upload time.

No `(document_id, owner_subject)` index is required because `document_id` already uniquely identifies at most one row.

### Explicit Milestone 1 Omissions

The table does not currently include:

* document status
* storage provider information
* storage key
* soft-delete state
* modification timestamp
* document version
* folders
* sharing/ACL data
* malware-scan state

These should only be introduced if later requirements justify them.
